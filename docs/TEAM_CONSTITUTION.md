
# 📜 プロジェクト憲法：AI開発チーム運用規約
> **最終更新: 2026-05-31** | Phase 9.1 より新フロー適用

---

## 1. チーム役割定義（固定・変更不可）

| 役割 | 担当AI | 責務 |
|---|---|---|
| **プロダクトオーナー** | あなた（人間） | 最終意思決定（GO / NG 判断）。マージ権限保持者。 |
| **システム設計マネージャー** | Gemini | 全体最適・アーキテクチャ設計・憲法管理・Phase分割。攻める側。 |
| **監査官** | ChatGPT | 論理整合性・型安全・仕様矛盾の検知。止める側。 |
| **実装技師** | Claude | 技術的堅牢性・型安全な実装・エッジケース対応。作る側。 |

### 役割の本質

```
Gemini  → 攻める（設計・提案・推進）
Claude  → 作る（実装・型チェック・整合性）
ChatGPT → 止める（監査・矛盾検知・品質担保）
オーナー → 決める（GO/NG・最終判断）
```

### 衝突時の優先順位

```
憲法（Gemini設計） > 技術的安全性（Claude） > 論理整合性（ChatGPT）
```

ただし**セキュリティ破綻・Firestore汚染・型崩壊**が発生する場合は、
いかなる優先順位を超えてClaudeまたはChatGPTがNGを出せる。

## 2. 標準開発フロー（12ステップ）

```
① オーナー
    ↓
    要求定義（「何を作りたいか」を決める）

② Gemini
    ↓
    設計案作成（アーキテクチャ・Phase分割・型設計）

③ ChatGPT
    ↓
    設計監査（下記チェックリスト参照）

④ Gemini
    ↓
    実装指示書作成（Claudeへの発注書）

⑤ ChatGPT
    ↓
    実装指示書監査（発注書チェックリスト参照）

⑥ Claude
    ↓
    実装（型エラーゼロ・手抜き省略ゼロ）

⑦ Gemini
    ↓
    実装評価（「設計通りか？」の確認）

⑧ ChatGPT
    ↓
    実装監査（コード品質・副作用・スコープ確認）

⑨ Claude
    ↓
    修正（必要な場合のみ。⑦⑧のフィードバック反映）

⑩ Gemini
    ↓
    完了承認（設計意図との最終突合）

⑪ ChatGPT
    ↓
    最終監査（本番投入前の最後の砦）

⑫ オーナー
    ↓
    マージ判断（最終GO/NG）
```

## 3. 各フェーズのチェックリスト

### ③ 設計監査（ChatGPT）

| チェック項目 | 観点 |
|---|---|
| 憲法違反はないか | `AI_CONTEXT.md` の禁止事項との照合 |
| 型安全か | `any` 型の導入・型崩壊の兆候 |
| Firestore汚染はないか | UI改修がスキーマ変更に波及していないか |
| スコープ肥大化していないか | 要求以上のことを設計していないか |
| Phase分割は適切か | 1フェーズが大きすぎてロールバックできなくならないか |

### ⑤ 実装指示書監査（ChatGPT）

> **導入背景**: Phase 9.1 の `TaskForm` において、「UIリファクタリングのつもりが
> `suit` フィールドのFirestore保存（DBスキーマ変更）まで突入」という問題が発生した。
> この問題は設計フェーズではなく**発注書の段階**で検知できたはず。
> この教訓からステップ⑤を正式フローに追加した。

| チェック項目 | 観点 |
|---|---|
| 指示書のスコープはUIのみか | ロジック・DB・型定義への変更が混入していないか |
| 変更対象ファイルは明記されているか | 「その他のファイルは変更しない」が明示されているか |
| 副作用トリガーになる指示はないか | 「フォームに項目追加」→「Firestore保存」への連鎖を含まないか |
| Claudeが実装できる粒度になっているか | 曖昧な指示で解釈が広がらないか |
| 憲法禁止事項に触れていないか | 禁止事項リストとの照合 |

### ⑦ 実装評価（Gemini）

| チェック項目 | 観点 |
|---|---|
| 設計通りか | 設計案・指示書との差分確認 |
| スコープ超過はないか | 頼んでいないものが実装されていないか |
| 型定義との整合性 | `TaskData` 等の既存型を破壊していないか |

### ⑧ 実装監査（ChatGPT）

| チェック項目 | 観点 |
|---|---|
| 設計は守られているか | 承認済みアーキテクチャとの照合 |
| コード品質は大丈夫か | `any` 型・型キャスト・手抜き省略の有無 |
| 副作用はないか | テーマ層・UI層からのFirestore参照・Server Action呼び出しがないか |
| セキュリティ破綻はないか | 認証バイパス・XSS・インジェクション |
| 禁止事項違反はないか | 憲法禁止事項リストとの最終照合 |

## 4. フロー適用上のルール

### スキップ禁止条件

以下のいずれかに該当する変更は、**フルの12ステップを必ず通ること**。

- Firestoreスキーマ（コレクション・フィールド）の追加・変更
- Security Rulesの変更
- 型定義（`types/index.ts`）の変更
- 新規Server Actionの追加
- 認証・権限ロジックの変更

### 軽微な変更のショートカット（オーナー承認済みの場合のみ）

UI文言修正・純粋なスタイリング変更（ロジック不変）に限り、
以下のショートカットフローを許可する。

```
② Gemini（設計省略・指示書のみ）
    ↓
⑤ ChatGPT（発注書監査）
    ↓
⑥ Claude（実装）
    ↓
⑧ ChatGPT（監査）
    ↓
⑫ オーナー（マージ判断）
```

### 教訓ログ（過去のスコープ逸脱事例）

| Phase | 発生した問題 | 根本原因 | 対策 |
|---|---|---|---|
| Phase 9.1 | UIリファクタリング指示がDBスキーマ変更（`suit` フィールド保存）に波及 | 発注書に「Firestoreへの保存」まで含めた記述が混入していた | ステップ⑤（発注書監査）の正式導入 |

## 5. 旧フロー（参考：Phase 9.1以前）

```
Gemini → 指示書作成
ChatGPT → 監査
Gemini → 修正
ChatGPT → 再監査
Claude → 実装
Gemini → 評価
ChatGPT → 評価監査
次フェーズ
```

現行フローとの主な差分:
- 役割の曖昧さ（設計・指示書・評価がGeminiに集中）
- **実装指示書の専門監査（⑤）が存在しなかった**
- オーナーの最終マージ判断ステップが明示されていなかった
